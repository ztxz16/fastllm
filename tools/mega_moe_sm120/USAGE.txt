Native SM120 MXFP4 EP kernel packages
===================================

Expert weights are repacked and their source allocations are retired one layer
at a time before serving. The native and grouped EP8 paths share the FP4 values. Each retains its own
scale layout. Temporary copies of the original weights are bounded to one layer.

On the shipped 110-SM EP8 geometry, auto uses grouped MoE for up to 128
collective rows per rank. With four ranks on each of two NUMA nodes and the
prefill pipeline enabled, it also uses grouped for fully dense prefill at
129–288, 384, 448, 480–768, and 2048 rows. The log reports
backend=sm120-auto-grouped-and-native. Above 128 rows all other shapes,
including uneven slices and masked verification, use native. EP4 uses native.
Set FASTLLM_SM120_EP_BACKEND=grouped or native to force a backend.

Packages in ftllm/kernels/mxfp4_ep/ require CUDA 12.9+ on Linux, a compatible
driver and direct peer access. Inference runs without the Python export tools.

SM120 builds with the grouped MXFP4 Tensor Core kernel also support EP when
the package or its model geometry does not match. Naive --ep 4/8 selects this
backend automatically for complete block-32 E8M0 experts, BF16 activations,
equal contiguous expert ownership and full P2P. Hidden and expert intermediate
widths must be multiples of 128. The number of SMs, expert count and top-k are
runtime parameters. The load log reports backend=sm120-grouped-ep. This path
is linked into FastLLM and requires no standalone cubin. Each rank sends one
quantized token per selected owner. Each owner computes only its routed rows.
Workspace and packed weights are prepared before capture. Tuned EP8 prefill
uses 1024-row chunks and can prefetch the following chunk on a copy stream. Set FASTLLM_SM120_EP_PREFILL_PIPELINE=0 for the 128-row workspace.
Other supported geometries use the 128-row workspace.

Currently shipped and tested packages:
  SM120, 110 SMs/GPU, EP4 and EP8, hidden=4096, intermediate=2048,
  256 experts, top-k=8, MXFP4 weights with block-32 E8M0 scales,
  BF16 input/output, MXFP8 internal activations.
  The default export covers powers of two from 1 through 2048 rows per rank.

Smaller row counts are masked to the next available bucket. Above the largest
bucket, all ranks execute the same number of chunks, including ranks with empty
local chunks. The largest bucket is a per-round capacity, not a maximum
inference batch size. Chunking also works within a captured parent CUDA graph.
Larger buckets reuse expert weights across more rows per dispatch. Each owner
holds complete experts. Expert tensor parallelism is 1 for both EP sizes.
The exporter compares direct return with rank-local combine, which sums local
expert contributions before returning them to the requesting rank. No runtime
tuning switch is required.
Both EP4 and EP8 pass native/source-lifetime and parent-graph replay checks.
Whole-model results depend on the measured parallel layout and input workload.

Local workspace sharing
-----------------------
Each bucket keeps its own CUDA virtual address range for its entire lifetime.
On devices with CUDA VMM support, transient local pages alias a per-rank physical
scratch pool. The exporter records two named private_ranges from the compiled
kernel layout. The nvlink_barrier_counter tracks the phase of the bucket's peer
signals. FC1 writes the block scales for FC2 into fc1_output_sf. Sharing the
pages covering those scales across bucket layouts caused corrupt MoE outputs
during speculative verification. Both ranges use private pages for the lifetime
of the bucket. The peer heap also remains private.

The pool belongs to one NativeEp instance, not to all models on a device. As with
the existing cross-layer bucket sharing, its invocations must be ordered. K1/K2
within one invocation use the same mapping; another bucket can reuse physical
pages only after that invocation completes. CUDA supports virtual aliases at
ordered operation boundaries:
https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/virtual-memory-management.html#virtual-aliasing-support

Physical storage grows by appending allocation-granularity blocks when a larger
bucket is prepared on the coordinator. Existing reservations and mappings never
move, so earlier graph executables and TMA descriptors stay valid. Preparation
must precede capture. Serving reuses prepared graphs without allocation,
remapping, recapture, or graph-executable updates. CUDA 12.x mapping offsets must
be zero, so each shared physical block is independently mappable. No compiler,
Python runtime, or new environment option is needed for sharing. Manifests
missing either named range and devices without VMM use dedicated allocations.

With the shipped packages and a 2 MiB allocation granularity, local workspace
backing across all buckets is 1030 MiB/rank for EP4 and 1922 MiB/rank for EP8,
excluding peer heaps, weights and other buffers. EP4 uses 966 MiB shared and
64 MiB private. EP8 uses 1856 MiB shared and 66 MiB private. Storage grows
as larger buckets are prepared.

Architecture scope
------------------
The exported graph loader requires SM120 and a matching package (including
SM count, EP size and model dimensions). Older CUDA toolkits and unsupported
devices retain the existing backend. Do not relax the architecture guard to
load these CUBINs on another SM.

Stable virtual addresses, append-only physical backing and build-time selection
are reusable techniques. Reusing them for another backend requires its own
workspace-lifetime metadata, ordered graph execution and compatible kernels.
In particular, private_ranges describes this pinned SM120 kernel's state; it
must not be copied to an SM90/SM100 package without auditing that kernel.
The arithmetic, TMA layouts and Green Context partition must be exported and
validated for the new target. No other architecture is enabled by this change.

Model widths, expert counts, top-k, EP size and SM partition are compile-time
specializations in the upstream kernels. This staging path requires hidden to be
a multiple of 128 and intermediate a multiple of 64; experts must divide across
EP ranks. Other alignments need padding or a fallback implementation.
A different tuple needs a new export to use the specialized split pipeline.
The Naive caller can use the built-in grouped EP implementation for its
supported alignments without exporting a package.

Build-only environment used for export:
  flashinfer-python 0.7.2
  nvidia-cutlass-dsl 4.8.0
  triton 3.8.0
  torch 2.14.1+cu130
  cuda-python 13.5.0, cuda-core 1.2.2
  CUDA 13 toolchain, 8 mutually peer-accessible SM120 GPUs

From the repository root, in that compiler environment:
  python tools/mega_moe_sm120/export.py \
    --ep 8 --hidden 4096 --intermediate 2048 --experts 256 --topk 8 \
    --output tools/fastllm_pytools/kernels/mxfp4_ep/sm120_sms110_ep8_h4096_i2048_e256_k8

Use --capacities to export a subset or an alternative set of row counts.
To regenerate EP4, use --ep 4 and its matching output directory.

The exporter reads compiled kernel objects and captured CUDA graph metadata.
It strips process addresses, emits explicit pointer/TMA/peer-offset relocations,
preserves dependency edge ports, and replaces Torch fill kernels with CUDA memset
nodes. It uses upstream compiler internals; keep the export environment pinned.
Only manifest.json and the referenced SHA256-named .cubin files are deployed.
For each capacity, the default --combine auto benchmarks both combine strategies
with deterministic nonzero weights/inputs and balanced/skewed routing. Repeated
child graphs exclude Python submission gaps. The measured time is the slowest
EP rank; both strategies use the established eight-warp K2 family without tail
reclaim. Output combination is compared with input caching disabled first.
Local combine must pass relative L2 <= 0.005, improve summed workload latency by
at least 5%, and regress neither workload by more than 5%. An unsupported or
slower local strategy retains direct return. Each bucket's selection field logs
the choice, measured times, numerical error and fallback reason. Only the winner
is deployed. --combine direct/local are build-time overrides for investigation;
they do not add inference options or dependencies. Calibration is specific to
the export GPUs and peer topology; re-export when that topology changes.
After selecting the combine strategy, the exporter benchmarks owner input
caching against that winner. This reuses a completed local activation copy when
the same source token visits another expert on the same GPU. An unfinished cache
entry falls back to a peer read instead of waiting, avoiding dispatch deadlocks.
Caching must preserve exact output and meet the same performance margin; each
bucket records dispatch_rank_cache, comparison timings and fallback reasons.
The captured recipe resets the transient cache before every replay. This is
per-invocation input reuse, not a cache across requests or decoding steps.

With --combine auto, the exporter tests a Green Context partition that gives
FC1 three fifths of the SMs, rounded down to the hardware alignment, and FC2
the remainder. It then tests up to four FC1 operand stages within the tile's
shared-memory and occupancy limits. Both trials use the same exact-output and
latency criteria as input caching. FC2 keeps its original pipeline depth.

Local combine rounds each owner's partial sum to BF16. The shipped EP4 package
uses local combine for 512, 1024 and 2048 rows. Its owner input cache is enabled
for 256, 1024 and 2048 rows. EP8 uses local combine and the owner input cache
for 256, 512, 1024 and 2048 rows. It also caches owner inputs at 128 rows.
Direct recipes clear the combine buffer before the collective start barrier,
so masked or invalid routes cannot reuse results from a previous replay. This
uses a CUDA memset graph node and does not add a compiled arithmetic kernel.
The regenerated calibration includes this clearing operation in direct recipes.
When regenerating artifacts, record the export tool revision and hashes in
third_party/flashinfer_sm120_ep/UPSTREAM.json. Retain the associated notices and
licenses when redistributing the packages.

The EP4 package contains 94 deduplicated binaries (8.1 MiB). EP8 contains
191 binaries (18.0 MiB) and a 7.1 MiB graph manifest. These include
BF16-to-MXFP8 staging, expert projection, FC2/combine and reduction kernels.
Rank-local combine uses an additional finalizer and rank-partial reduction.
