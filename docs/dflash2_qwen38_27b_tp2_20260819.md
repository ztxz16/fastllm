# Qwen3.8-27B DFlash2：双 RTX 5090 复现、FastLLM 接入与性能分析

测试日期：2026-08-19

## 结论

- DFlash2 需要同时加载目标模型 `/root/hfmodels/Qwen3.8-27B-FP8` 和独立 draft 模型 `/root/hfmodels/Qwen3.8-27B-DFlash2`。MTP 不需要独立 draft 目录，目标模型中已有 `mtp.safetensors`。
- FastLLM 已接入 DFlash2，代码提交为 `3537f057a8e708cef0c8bc5e3889d520c57630f0`。DFlash 和 MTP 使用不同的 draft backend，共享原 MTP verifier、cache commit 和 rollback 路径。
- DFlash sampling 已改成和 SGLang 相同的 rejection sampling 语义：draft selector 产生稀疏分布 `q`，target 按 temperature → top-k → top-p 得到 `p`，逐 token 以 `min(1, p(x)/q(x))` 接受，拒绝时从归一化的 `max(p-q, 0)` 采样。
- 在接入初始版本的同一套 128 题 GSM8K、单并发、block=6 无插桩实测中，FastLLM 为 **123.51 tok/s**，SGLang 为 **178.50 tok/s**。SGLang 快 44.52%，或者说 FastLLM 吞吐低 30.81%。
- 两边最终数值答案均为 **120/128 = 93.75%**，逐题有 124/128 个数值答案相同；FastLLM 和 SGLang 各自独对 1 题，没有可测的精度差异。
- FastLLM 平均单步提交长度为 **4.071**，SGLang 为 **4.590**，FastLLM 低 11.31%。即使线性假设 FastLLM 获得相同接受长度，估算也只有 139.26 tok/s，仍比 SGLang 低约 22%，所以接受率不是主要性能差距。
- nsys 波形显示，主要差距是执行方式：FastLLM 的 target verify 没有覆盖整段 speculative CUDA Graph，GPU 忙碌率只有 25.0%；SGLang verify graph 的忙碌率为 91.6%。FastLLM DFlash backbone 又只在 root GPU 执行，而 SGLang draft 使用 TP=2 和 CUDA Graph。
- accept/rejection sampling 本身不是瓶颈：FastLLM 平均 GPU span 为 0.322 ms，SGLang 为 0.215 ms，绝对差只有约 0.11 ms。
- MTP 固定流回归的最终中位数为 259.084 tok/s，相对 `e61c7ce8` 基线的 260.831 tok/s 为 -0.67%，相对 sampling 改动前的 260.857 tok/s 为 -0.68%；输出哈希不变，差值低于本机单次运行波动。
- 后续优化提交 `f7c8535b..161962de` 将相同 512-token 固定流的 B6 从 **207.69** 提升到 **285.90 tok/s（+37.66%）**，B8 从 **150.21** 提升到 **379.07 tok/s（+152.36%）**；两者输出哈希均不变，B8 现在比 B6 快 32.59%。
- 最终 B8 的 128 题非 greedy GSM8K 为 **207.06 tok/s、120/128（93.75%）**，正确率与初始 FastLLM B6 相同；相对初始 FastLLM B6 提升 67.65%。当前推荐使用 checkpoint 原生 block=8。

## 后续优化与最终验收

本节记录 `f7c8535b..161962de` 的后续优化。本文后面的原始 nsys 数据仍保留为接入初始版本 `3537f057` 的瓶颈基线，不能用来代表最终 eager 路径。

主要改动包括：

- 将 DFlash dynamic convolution、QKV 准备、门控激活、KV 物化/压缩/直写缓存和滑窗注意力融合为专用 CUDA 路径。
- 合并 QKV、gate/up 以及跨层 KV 投影，减少小 kernel、临时 tensor 和 host dispatch。
- 将两卡 lm_head 的分片 top-k 与归并移到 CUDA/P2P 路径，只把最终少量候选送回 selector。
- 分级预分配 draft KV cache，避免长输出期间反复扩容。
- 为 6-token FP8 投影选择更高并行度的原生调度，并把 Qwen3.5 线性注意力/卷积快照上限从 6 扩到 8，使 B8 不再进入通用隔离缓存与 replay 路径。

### 评估后未保留的方案

所有候选都先检查固定流哈希，再做同二进制 A/B；负收益代码均已回退：

- 现有全局 CUDA Graph 模式保持正确，但 B8/1024 慢约 1.24%。为 64 层 dense MLP 单独建图也保持正确，但因每层固定缓冲拷贝与小图 dispatch 慢 2.83%。B8 verify 还包含动态 paged-KV 位置、七份前缀快照和 rollback/commit，不能直接放宽现有单 token graph 条件。
- 将约 250 MiB selector codebook 常驻 GPU 的版本保持正确，但端到端慢约 0.03%，没有达到可提交的提升门槛。
- CUTLASS 非交换 ping-pong 调度慢 9.39%，交换布局 ping-pong 慢 0.58%；原生 n=8 FP8 rows=2/rows=1 分别慢 2.79%/3.48%。因此最终继续使用确定性的 SwapAB cooperative CUTLASS 路径。
- 这些实验没有以“接近持平”为由提交；只有正确性通过且重复测速明确提升的改动进入上述 13 个优化提交。

## FastLLM 实现

### 使用方式

```bash
ftllm server /root/hfmodels/Qwen3.8-27B-FP8 \
  --model_name Qwen/Qwen3.8-27B \
  --dtype auto --tp 2 --cuda_embedding --max_batch 1 --tokens 8192 \
  --host 127.0.0.1 --port 18126 --hide_input \
  --speculative_algorithm dflash \
  --speculative_draft_model_path /root/hfmodels/Qwen3.8-27B-DFlash2 \
  --speculative_num_draft_tokens 8
```

`--speculative_num_draft_tokens` 表示包含 anchor 的 block 大小，因此 block=8 实际提出 7 个 draft token。省略 `--speculative_algorithm dflash` 时，CLI 会从 draft checkpoint 的 `architectures=["DFlash2DraftModel"]` 自动识别。省略 block 参数时使用 checkpoint 的 block=8；最终优化版本也推荐这一原生形状。

### Draft 和 verifier 的边界

- checkpoint loader 读取独立的 DFlash2 `config.json` 和 safetensors，并映射到 `dflash.*` 命名空间。
- target forward 只在 DFlash 请求中捕获 5 个指定层的 hidden state；普通 decode 和 MTP 不产生这些副本。
- `runMtpDraftChain` 保留原来的逐 token MTP draft 实现；`runDFlashDraftChain` 独立运行 DFlash block draft；薄分发层 `runSpeculativeDraftChain` 只负责选择 backend。
- 两个 backend 后面的 target verify、接受长度处理、target KV commit、线性注意力 rollback 和下一轮输入构造共用同一套代码。
- DFlash request 创建、结束和异常回滚会清理独立的 draft KV/cache；不会复用或修改 MTP draft cache。

### Sampling 与 SGLang 对齐

非 greedy DFlash 不再走 MTP 的 typical acceptance，而是使用下面的 SGLang/DFlash rejection sampling 语义：

1. DFlash 每个位置先取 target lm_head logits 的全局 top-16 候选。
2. selector 将候选 logit、当前 hidden projection、predecessor/successor codebook 合成 score。
3. 对 `score / temperature` 做稳定 softmax，在 top-16 上逐位置采样；上一个采样 token 作为下一个位置的 predecessor。该稀疏概率即 draft 分布 `q`。
4. target verify 一次计算 anchor 和所有 draft 位置的 logits；依次应用 temperature、top-k 和 top-p，并重新归一化成 `p`。
5. FlashInfer `ChainSpeculativeSampling` 按 `u × q(x) < p(x)` 接受 draft；首次拒绝时从 `max(p-q, 0)` 的归一化残差中恢复采样；全部接受时再从 bonus row 采样一个 token。

target probability filtering、稀疏 `q` scatter 和 chain rejection 都在 CUDA 上完成。MTP 仍使用原来的 typical acceptance，因此这次语义修改不会改变 MTP 的采样路径。

正确的 rejection sampling 保持 target 分布，但 FastLLM 与 SGLang 使用独立 RNG，不能要求两边逐 token 文本相同。验证分为三层：CUDA 分布 smoke test、greedy 固定 token 流哈希，以及 GSM8K 逐题答案精度。

### 当前并行方式

- target verify 使用 TP=2。
- DFlash 5 层 backbone 和 selector hidden projection 当前只在 root GPU 执行。
- target lm_head 使用两卡 vocab shard；每卡先做 local top-16，再在 CPU 合并 `TP × 16` 个候选，避免通过 PCIe 汇聚完整 `[block, vocab]` logits。
- predecessor/successor codebook 保存在 CPU，避免 root GPU 再占约 250 MiB；selector rank-256 打分也在 CPU 完成。

这套布局控制了显存和 PCIe 流量，但会引入每轮两卡同步、少量 D2H 和 CPU selector 工作，是当前 draft 波形长于 SGLang 的一部分原因。

## Benchmark 方法

### GSM8K 端到端

- 数据集：`openai/gsm8k` test split。
- 使用 `Random(42)` 打乱，取完全相同的前 128 题；第 129 题只做 warmup。
- prompt：原问题加 `Please reason step by step, and put your final answer within \boxed{}.`。
- 参数：concurrency=1、reasoning=xhigh、temperature=1、top_p=0.95、top_k=20、max_new_tokens=4096、block=6。
- 吞吐按所有 completion token / 128 题墙钟时间计算，正式数据不带 nsys/NVTX 插桩。
- 精度先提取最后一个 `\boxed{}` 内的数值；没有合法 box 时再回退到全文最后一个数值。报告同时给出 boxed 和 fallback 口径。

sampling 会使不同后端消耗不同随机数，进而改变文本长度和 EOS 位置。因此端到端 tok/s 是服务实测，不是相同 token 流的 kernel A/B；精度比较也应看总体和逐题正确性，而不是文本完全一致率。

### nsys 固定输出

- 单请求、temperature=1、top_p=0.95、top_k=20、强制输出 512 token、block=6。
- FastLLM 记录到 128 个 verify iteration；SGLang graph-level 记录 115 个、node-level 记录 118 个。
- SGLang 分别使用 CUDA graph-level trace 和 graph-node trace。graph-level 用来测整个 graph 执行时间，node-level 用来计算 range 内 kernel 的 busy union。
- 临时 NVTX range 只标记 `draft`、`verify`、`accept`，分析后已经从 FastLLM 和 SGLang 环境移除，不在提交中。
- FastLLM workload 将输入 pad 到 128 token，SGLang 原始文本为 45 token；输出过程中两边上下文区间大幅重叠。绝对 phase span 会有少量上下文长度偏差，下面的 GPU busy ratio、graph replay 和 host launch 碎片结论不依赖这项差异。

## 速度与精度结果

### 接入初始 sampling：FastLLM 对 SGLang

| 后端 | 输出 token | 总耗时 | 吞吐 | 平均提交长度 | fallback 正确 | boxed 正确 | box 提取成功 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| FastLLM DFlash2 B6 | 72584 | 587.664 s | **123.51 tok/s** | **4.071** | **120/128 (93.75%)** | 119/128 (92.97%) | 124/128 (96.88%) |
| SGLang DFlash2 B6 | 67079 | 375.788 s | **178.50 tok/s** | **4.590** | **120/128 (93.75%)** | 120/128 (93.75%) | 126/128 (98.44%) |

速度关系：

- SGLang / FastLLM = **1.445×**，即 SGLang 快 44.52%。
- FastLLM / SGLang = **69.19%**，即 FastLLM 吞吐低 30.81%。
- 这次 SGLang 的 178.50 tok/s 与前一次 sweep 的 B6 176.91 tok/s 只差 +0.90%，说明官方基线稳定。

FastLLM 五个 draft 位置的累计接受率为：

```text
86.96%, 72.22%, 59.30%, 48.64%, 39.93%
```

所以平均提交长度为 `1 + Σ acceptance = 4.0705`。SGLang response metadata 给出的平均值为 4.5895，FastLLM 低 11.31%。如果只把 FastLLM 的输出/verify 线性放大到 SGLang 的接受长度，估算吞吐是 139.26 tok/s，仍比 178.50 tok/s 低约 22%；执行时间差仍占主导。

两边 fallback 正确性的逐题列联结果：

| 结果 | 题数 |
| --- | ---: |
| 两边都正确 | 119 |
| 只有 FastLLM 正确 | 1 |
| 只有 SGLang 正确 | 1 |
| 两边都错误 | 7 |

最终数值预测有 124/128 相同。120/128 的 95% Wilson 区间约为 88.15%–96.80%，而配对差异恰好是 1 对 1；当前样本没有证据说明任一后端精度更高。boxed 口径的一题差异主要是输出格式/提取率差异，不应解释为模型推理能力差异。

输出长度分布也说明为什么不能直接用总耗时比较延迟：FastLLM 平均 567.1、median 265、6 题达到 4096 token；SGLang 平均 524.1、median 272、4 题达到 4096 token。吞吐已经按实际 output token 归一化。

## nsys 波形分析

### 三阶段对比

下面是 graph-node trace 中每轮对应 GPU projection 的平均值。GPU busy 是该 phase 内 kernel/memcpy/memset 时间区间的并集；verify 和 SGLang draft 按每个 rank 统计，FastLLM draft 只有 root GPU。

| Verify | 28.792 ms | 7.229 ms | **25.0%** | 14.612 ms | 13.381 ms | **91.6%** | 1.97× |
| Accept | 0.322 ms | 0.233 ms | 72.3% | 0.215 ms | 0.145 ms | 67.0% | 1.50× |

FastLLM 三段 span 合计约 52.11 ms；profiled workload 实际每个 validation 约 54.05 ms，平均提交 4.0 token，对应 75.12 tok/s。nsys 对 FastLLM 大量细粒度 CUDA API 的放大明显，因此这个吞吐不能代替无插桩的 123.51 tok/s。

SGLang 完整 speculative loop 平均约 24.21 ms，其中还包含 phase 间的异步等待和调度 gap。graph trace 中平均提交约 4.452 token，`4.452 / 24.21 ms = 183.9 tok/s`，和无插桩 178.50 tok/s 接近。

### Verify 波形

SGLang target verify 是稳定的 CUDA Graph replay：

- 每 rank 的 target graph 平均执行 **14.46 ms**。
- node trace 里 verify span 为 14.61 ms，其中 GPU busy 13.38 ms，波形基本连续。
- Python/NVTX 看到的 verify launch 只有约 0.81 ms，那只是异步提交时间，不能误当成 target forward 的执行时间。

FastLLM speculative verify 当前没有被整段 CUDA Graph 覆盖：

- span 为 28.79 ms，但实际 GPU busy 只有 7.23 ms；约 75% 的范围是 kernel 之间的 host launch、同步和资源准备空隙。
- 128 个 validation 中共出现 334871 次 `cudaLaunchKernel_ptsz`、77816 次 `cudaMemcpy2D`、47592 次 memset、20041 次 memcpy，另外有 658 次 device sync 和 268 次 stream sync。
- target FP8 projection 的调用形状匹配：FastLLM 共 65536 次，SGLang 共 60416 次，折算都是每 rank 每 verify 约 256 次。因此波形差异不是少算了一部分 target 层，而是相同量级工作以不同方式提交。
- FastLLM 的主要 FP8 GEMV 平均 37.47 µs，SGLang Blackwell CUTLASS kernel 平均 33.46 µs，FastLLM 单 kernel 约慢 12%。这会贡献约 1 ms/verify，但远小于 graph/launch gap。

结论：verify 的第一优化项是为 block=6 的 target speculative forward、TP reduce 和必要 metadata 更新建立可复用 CUDA Graph，而不是先优化 rejection kernel。

### Draft 波形

FastLLM draft span 23.00 ms，SGLang 6.91 ms，差 3.33 倍。它同时包含计算量和调度方式差异：

- FastLLM 5 层 DFlash backbone 只在 GPU0 执行；GPU1 只参与 vocab-sharded target lm_head。SGLang 在两张卡上执行 TP draft graph。
- FastLLM draft 的 GPU busy 4.58 ms，本身已经是 SGLang 2.55 ms 的约 1.8 倍；root-only backbone 是主要原因。
- FastLLM busy ratio 只有 20%，说明 generic operator 的大量小 kernel 和 host dispatch 又把 4.58 ms 工作拉长到 23.00 ms。
- 每轮两卡 lm_head local top-k 后需要 stream sync、D2H 和 CPU merge。profile 中 top-k 相关调用平均约 1.60 ms；随后 rank-256 selector/codebook 仍在 CPU。
- SGLang 的纯 draft CUDA Graph replay 每 rank 约 2.56–2.58 ms；完整 draft phase 还包含约 4 ms 的准备/调度，但仍显著短于 FastLLM。

结论：draft 的第一优化项是把 5 层 backbone 做 TP=2 并 graph capture；第二项是把 lm_head top-k merge、selector score 和路径采样留在 GPU，去掉每轮 D2H/CPU selector 边界。

### Accept 波形和接受率

FastLLM accept 的 CUDA kernel 合计约 0.23 ms/step，主要组成是：

| 操作 | 平均时间 |
| --- | ---: |
| top-p renorm | 97 µs |
| temperature softmax | 63 µs |
| chain speculative sampling | 45 µs |
| top-k renorm | 20 µs |
| sparse `q` scatter | < 1 µs |

FastLLM accept span 比 SGLang 多约 0.107 ms。即便完全消除也只占 FastLLM 一轮约 54 ms 的 0.2%，不是吞吐差距来源。

接受率差异会线性影响每次昂贵 verify 能提交多少 token。FastLLM 当前 4.071 对 SGLang 4.590，少 11.31%。sampling 语义已经一致，因此下一步应核对 draft backbone 的 BF16 数值、dynamic convolution/attention 实现、selector top-k tie/rounding 和 codebook 计算，而不是放宽 acceptance 条件；放宽会破坏 target 分布正确性。

## 比 SGLang 慢的原因排序

1. **Target verify 没有整段 speculative CUDA Graph。** 这是最大差距：FastLLM verify span 是 SGLang 的 1.97 倍，GPU 忙碌率却只有 25.0% 对 91.6%。
2. **Draft backbone 为 root-GPU-only 且未 graph capture。** draft span 是 SGLang 的 3.33 倍；纯 GPU busy 也约为 1.8 倍。
3. **平均提交长度低 11.31%。** 它会放大前两项成本，但单独不能解释 44.52% 的端到端差距。
4. **lm_head/selector 有跨设备同步和 CPU 边界。** 两卡 local top-k 后的同步、D2H、merge，以及 CPU codebook selector 都位于每轮关键路径。
5. **FP8 projection kernel 稍慢。** FastLLM 主要 kernel 平均慢约 12%，是次要但稳定的差距。
6. **Rejection/accept 不是主要问题。** 两边绝对只差约 0.11 ms/step。

建议按 1 → 2 → 4 → 5 → 3 的顺序优化。接受率调查应保持 rejection sampling 数学语义不变，以数值对齐方式修正。

## 当前限制

- DFlash 当前使用单 scheduler lane，本文只测 concurrency=1。
- 强烈建议搭配 `--cuda_embedding`，否则 draft block 可能走 CPU embedding。
- DFlash backbone 当前没有 TP 分片；双卡主要加速 target verify 和 vocab-sharded lm_head。
- long prefill 为保证 DFlash target hidden/KV 对齐，暂不走现有 MTP chunked-prefill 特化。
- 最终版本建议 block=8；快照和原位验证快路径当前上限也是 8。更大的 block 仍会进入通用路径，并且超出该 DFlash checkpoint 的训练形状。
- DFlash target/draft 尚未启用整段 CUDA Graph；现有图方案实测为负收益，动态 paged-KV metadata 也不能安全套用单 token graph。
- sampling 输出由独立 RNG 驱动，跨后端的逐 token 文本或输出长度不应作为正确性条件。
